Two Solvers, One Vortex

01 What the paper actually contains

The comparison was to be driven by Wingrove & Bach's analysis of twelve severe clear-air turbulence incidents, restricted to aircraft that exist in JSBSim's library. That restriction cannot be applied, for a reason worth stating plainly at the top: the paper never names a single aircraft type.

Every case is “modern airliners” carrying a digital flight-data recorder. Table 1 gives date, location and altitude; Table 2 gives load increments. No table, figure or sentence identifies an airframe. So the aircraft had to come from somewhere else — here, from the intersection of what JSBSim ships with what AtiSim holds.

What the paper does supply

Fig. 4 (p. 755) gives three identified vortices as core diameter and tangential velocity: Hannibal 1000 ft at 85 ft/s, Morton 900 ft at 70 ft/s, Cimarron 900 ft at 50 ft/s. It draws a single core with the flight path through it, and one up-spike followed by one down-spike — which is the encounter modelled here.

02 Which aircraft, and why

JSBSim ships 737 and B747 (not 747 — the directory name is why a search for it comes up empty). AtiSim holds a 737, two 747 configurations, a Cessna 172 and a PA‑28. The light aircraft cannot reach FL330–FL390, so the working set is the two airliners.

The 737 needed nothing: AtiSim's entry was recovered from JSBSim, so mass, wing area, span, chord and the full inertia tensor match to under 0.1%. The 747s did not match at all.

Since n = L/W, a load-factor difference between two engines flying “a 747” would have been that 15.5% mass gap and nothing about either solver. So a second entry, boeing747_jsbsim, was recovered from JSBSim's own running engine using the same machinery that recovered the 737 — after which both engines carry identical mass, geometry and inertia by construction. The CR‑2144 boeing747 is untouched and remains the validated aeroplane.

This entry is not a credible 747

B747.xml declares release="ALPHA", author “Unknown”, and the same disclaimer the 737 carries. More specifically: its CLα table is (−0.20, −0.68), (0.00, 0.20), (0.23, 1.20), (0.60, 0.60) and the 737's is (−0.20, −0.68), (0.00, 0.20), (0.23, 1.20), (0.46, 0.20). The first three points are identical, and both give CLα = 4.348 /rad. A 747 and a 737 do not share a lift-curve slope; this is one Aeromatic template used twice. It costs the solver comparison nothing — both engines eat the same numbers — and it makes any comparison of that entry against flight data meaningless.

Case assignment then follows from the 737 entry's declared validity band of 25,000–35,000 ft: Cimarron at 33,000 ft is the only case inside it, and it is also the only case with published time histories. Hannibal (37,000 ft) and Morton (39,000 ft) fly the recovered 747, whose band is 35,000–41,000 ft.

03 Making it a comparison rather than two runs

Five things had to be established before any difference could be attributed to the solvers. Each is measured, and each could have failed.

One more, which turned out to matter more than expected: the two engines do not trim to the same point. JSBSim's do_simple_trim converges to Nz = 0.99093, not 1.0; AtiSim needs 0.95% more lift coefficient for a true 1 g, worth +0.063° of α against the +0.054° observed. So AtiSim is started from JSBSim's recorded body-velocity vector, rates, attitude and achieved surfaces, rather than from its own trim. That buys an identical initial condition — and, as §5 shows, costs something else.

05 The pitch result, and why it is not what it looks like

Measured the obvious way — as an excursion from the trim attitude, which is how Wingrove & Bach report theirs — the same runs disagree on pitch by 15% to 54%. That number is real, reproducible, and almost entirely an artefact of the measurement.

The same runs, measured from trim

Hannibal−4.3%−42.8%1.553°
Morton−6.0%−53.7%1.482°

The run-in is fifteen core radii — nine to eleven seconds — through the vortex's 1/r far field before the core is reached. Attitude accumulates over that. By the time it reaches the window edge on Hannibal, AtiSim is already 1.55° nose-down of JSBSim, and the “44% disagreement” is that offset carried into the event, not a disagreement about the event.

The general point

Load factor is algebraic in the state — it depends on where the aircraft is now, not how it got there — so it does not accumulate. Attitude is an integral, so it does. That is the whole of the difference, and it is why the load column looked fine from the start while the pitch column looked alarming. A cross-code comparison that reports attitude excursions from a datum far upstream of the event is measuring its own run-in.

Two experiments that close it

The suspect was the trade made in §3: AtiSim is started from JSBSim's trim state, which is 0.95% of CL short of AtiSim's own 1 g, so AtiSim begins fractionally out of trim. Two runs settle whether that is really the cause.

Switch the vortex off entirely. Fly the same start state, the same controls, the same duration, in still air. Whatever pitch appears cannot be the vortex.

So the answer is

The 15–54% pitch error is not a disagreement between the solvers and is not slow integration of a physical difference. It is one modelling choice — the decision to give both engines an identical start — costing 0.95% of lift coefficient, paid back over eight to nine seconds of settling. Start each engine in its own trim and the same measurement agrees to 1%. The core response never moved, because the settling is slow compared with a one-second traverse.

06 What JSBSim structurally cannot carry

JSBSim samples the wind at a single point. Its property catalog reports atmosphere/p-turb-rad_sec, q-turb-rad_sec and r-turb-rad_sec as read-only, and a write to q-turb-rad_sec reads back 0.0 after one step. Every writable wind input — wind-*-fps, gust-*-fps, turb-*-fps, cosine-gust/* — is translational.

So the gust gradient across the airframe has no injection point. Against a 900–1000 ft core and a 64 m span that is not a small omission, and AtiSim can be used to measure it. The gradient splits into two physically distinct terms, and they pull in opposite directions — so reporting them together would have hidden both.

The wind-induced ɑ̇ term reduces the load excursion by up to 11%; the gust-rate term increases it by up to 20%. Net, the gradient adds 8–13% of load span. That is the size of the term JSBSim has no way to represent, and it is the single largest modelling difference this comparison found — roughly five times the solver-to-solver disagreement.

07 Against the DFDR data

Only Cimarron can be tested this way. Hannibal and Morton fly the JSBSim-derived 747, which is not a credible aeroplane; and the paper never says what any of the real aircraft were.

JSBSim+0.4357 g−0.8263 g+2.883°−2.301°
AtiSim, translational+0.4171 g−0.8408 g+2.401°−2.645°
Wingrove & Bach, DFDR+0.73 g−1.20 g+1.80°−0.50°

Both engines under-predict the recorded load by 30% on the negative peak and 40–43% on the positive one, and over-predict the pitch excursion, in the same direction and by similar amounts. That is the informative part. Where two independent solvers agree closely with each other and both depart from the measurement, the discrepancy is not in either solver — it is in what they were both given: the single-core Rankine vortex, the traverse geometry, the aircraft that is not the aircraft the DFDR was recording, and the assumption that the encounter is a clean perpendicular pass through one core centre.

The qualitative pattern the paper describes does survive: pitch down as the aircraft meets the up-gust, then up through the down-gust. Both engines reproduce that ordering. They simply do more of it, against less load, than the recorder saw.

Which shared input is responsible

Start from what the aircraft would feel if it could not respond at all. A 50 ft/s gust at 766 ft/s is Δα = 3.74°; at CLα = 4.348 and CL,trim = 0.391 that is a quasi-steady +0.725 g — almost exactly the DFDR's +0.73. The simulated aircraft reports +0.417, so it sheds 42% of the quasi-steady load by pitching away and climbing during the one-second traverse.

So the question is which shared input is wrong. Changing one at a time, against the recorded −1.20 g:

Gust strength dominates. A 40% stronger core closes the gap almost exactly, and there is direct evidence for it in the source: Fig. 4 overlays the Cimarron data on the fitted model, and the data spikes past it. The Rankine core is a smooth fit to a signal that was not smooth, and a fit that matches a peak in the least-squares sense under-reads the peak itself.

Lift-curve slope is worth about half the remainder. JSBSim's table gives 4.348 /rad with no Mach correction; Prandtl–Glauert at M 0.78 would raise it by a factor of 1.60. That alone takes 70% to 85%. Both engines inherit the same table, which is precisely why they agree with each other and miss the data together.

A clean negative result

Airframe mass does not matter. The obvious intuition — a heavier aircraft has more pitch inertia, so it sheds less of the quasi-steady load — is wrong. Flying the same vortex with the 747 at four times the 737's mass and twenty times its pitch inertia moves the answer by 0.6%. The reason is that Δn = ΔCL/CL,trim and CL,trim = W/q̄S, so wing loading cancels. Not knowing what aircraft the DFDR was in is a real limitation of this comparison, but it is not the source of this discrepancy.

08 The Hannibal radius, decided

PARKS_CASES gave Hannibal a 600 ft core radius, transcribed from Parks et al. 1985. Wingrove & Bach Fig. 4 gives the same vortex a 1000 ft diameter — 500 ft. Everything above is flown at 500 ft.

The units are not in question. Fig. 4's Morton row halves to 450 ft, which is the code's Morton radius to the digit — that agreement is what establishes the column as a diameter and makes Fig. 4 a checked source rather than a guess. The paper's own summary text (p. 760) says the same thing in words: “the vortex cores have diameters of 900–1000 ft”.

The evidence pointing the other way, recorded

Parks p. 128 checks its identified arrays against Scorer's theory: “the ratio of spacing to core diameter ranged from about 2.9 to 3.5.” At 600 ft the two cases give 2.92 and 3.56 — that sentence, reproduced. At 500 ft they give 3.50 and 3.56, and the lower end of Parks' stated range is gone.

A transcription error in a radius would normally break its consistency with a separately quoted ratio range. These two agree at 600 ft, which is what a faithful transcription looks like. Against that: the ratio quote and the 600 ft come from the same unretrieved document and the same transcriber, so they are not independent evidence — one table misread carries into both. Wingrove & Bach is in hand and says 1000 ft twice, in a figure and in prose.

The two papers disagree and only Parks 1985 — J. Aircraft 22(2), 124–129 — can close it. The superseded value is kept in the code as a named constant, and the test that checked Scorer's ratio now pins both numbers so the argument survives where someone will find it.

What the radius is worth, measured before it was fixed: at 600 ft the peak load was −1.1325 g, at 500 ft it is −1.2581 g — an 11.1% spread. The choice is not cosmetic.

Morton remains the control that makes the whole radius question tractable: both sources give it 450 ft, its two runs are the same case flown twice, and they agree to the last digit. That is also, now, the only determinism check on the harness end to end.

09 Limits

  • Neither engine is validated against reality here. Both JSBSim models carry the same disclaimer — built from public data, technical reports, textbooks “and guesses”, for educational use. This is a comparison of two implementations fed the same numbers, not a statement about a real 737 or 747.
  • The 747 arm is doubly synthetic. boeing747_jsbsim exists to make the two engines carry identical mass and geometry; its lift curve is a 737 template.
  • Single core, not the Parks array. Matching Fig. 4's own model. A second core would add an event whose overlap depends on a spacing Fig. 4 does not give, and which Cimarron has no published value for at all.
  • Wave drag is untested. Both engines return exactly zero at these Mach numbers by construction.
  • The strip-theory load path is unavailable for every JSBSim-recovered entry: neither 737.xml nor B747.xml defines CLq, so the effective tail arm −Cmq/CLq is a division by zero. It costs this work nothing — strip loads are roll-only and this field has no spanwise structure — but the gradient arm rests on the analytic Jacobian alone, with no independent cross-check.
  • The run-in drift is now explained (§5) but not eliminated: the headline table still uses the shared start, because an identical initial condition is worth more to a cross-code comparison than a tidier from-trim column. Read the core-response numbers, not the from-trim ones.
  • Parks 1985 is still unretrieved, and its Scorer ratio check disagrees with the radius now flown (§8).

10 Reproducing it

Two interpreters, deliberately. The project venv has no JSBSim; three scripts under scripts/ import it, run under a separate Python 3.10, and freeze their output to checked-in XML so the test suite runs anywhere and reference drift shows up in git diff. 

# 1. recover the 747 entry from JSBSim's running engine
<ref-python> scripts/gen_jsbsim_747.py

# 2. freeze JSBSim's answer to the five vortex encounters
<ref-python> scripts/gen_jsbsim_vortex_reference.py

# 3. fly AtiSim through the identical field and compare
.venv/Scripts/python.exe scripts/vortex_compare.py --png runs/vc.png

# 4. separate the two large errors into their causes
.venv/Scripts/python.exe scripts/vortex_diagnose.py
Two bugs the tests caught, worth recording

The Ixz sign was inverted. inertia_tensor negates its argument and JSBSim's property is already the tensor element, so the engine's −970,000 had to be passed as +969,999.99. This is the exact error the 737 shipped with once — worth 1.6–3.2% on the lateral modes and inside every layer tolerance. It was caught only because the test compares the assembled tensor against the frozen reference rather than the argument against a remembered convention.

A unit constant differing in the eighth digit. Values converted with 1.35581796190452 instead of the project's own 1.3558179483314003 left a 1e−8 relative gap. Recomputed correctly, Izz and Ixz land on B747.xml's stated values to ten digits — which is itself the check that the recovery is a recovery.

The recovery is verified by landing on B747.xml's own declared constants: CYβ, Clβ, Clp, Cldr, Cnβ, Cndr and CLδe exactly; Cmα at −0.699965 against −0.7000; and Cmq + Cmα̇ = −25.000000 against −21 and −4. The individual split is ill-conditioned — the two are nearly collinear, at a design condition number of 2.7e9 — so the sum is the quantity that carries weight, exactly as the 737 entry already records.
